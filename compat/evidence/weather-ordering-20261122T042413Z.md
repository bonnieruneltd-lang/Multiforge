# Master-sequenced weather live evidence 20261122T042413Z

Two Forge 1.20.1 dev servers (`live1` 25565, `live2` 25566) and the standalone master;
current build with `WorldWeatherManager`. Two headless bots (`WeatherBotA` on `live1`,
`WeatherBotB` on `live2`, `minecraft-protocol` 1.68.0) recorded the clientbound
`game_state_change` packets.

## 1. Master versions do not churn

`weather rain 6000` on `live1` and, three seconds later, `weather clear 6000` on `live2`
produced exactly two semantic versions per world in the master log:

```
[04:24:10 INFO] ... Weather world version 1 from live1: rain=true, thunder=false
[04:24:13 INFO] ... Weather world version 2 from live2: rain=false, thunder=false
```

Only four `Weather world version` lines exist in the whole run (overworld plus the two
dimension worlds per transition). The earlier build, before the semantic-dedupe and
skip-one-poll fixes, advanced to version 24 in six seconds because every server echoed the
other's timer values. That regression is covered by `identicalWeatherDoesNotAdvanceVersion`.

## 2. Both clients observe the same transitions

Both bots logged the rain level rising to 1 and then falling back to 0:

```
[bot] GAMESTATE reason=rain_level_change value=0.009999999776482582
...
[bot] GAMESTATE reason=rain_level_change value=0
```

`grep -c GAMESTATE` reports 205 events on live1's bot and 135 on live2's; the difference is
only the animation sampling rate, both saw the start and end of rain. The clientbound
`game_state_change` packets are generated by the servers' own levels, so this proves the
applied state, not only the master bookkeeping.

## 3. Paths covered

* A server that connects later receives the current state in the hello replay
  (`weatherStateIsReplayedWhenAServerConnects`).
* Versions are per world (`weatherVersionsAreIndependentPerWorld`), so the nether/end
  bookkeeping cannot advance the overworld version.
* Same-flags reports with different timers are stored for replay but do not broadcast
  (`identicalWeatherDoesNotAdvanceVersion`).
* A reconnecting server reports its local weather after the master replay, so a change made
  through the peer fallback during an outage is not rolled back.

## 4. Limits

The version is a master-arrival order, not a wall-clock timestamp; two reports that arrive in
the same millisecond are ordered by the master lock. Weather timers still decrement locally
between transitions, so the synchronized duration can differ by up to one poll interval. If the
master is down, the old peer `WeatherUpdatePacket` last-writer-wins path is still used.

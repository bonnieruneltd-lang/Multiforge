# Boss bar replication live evidence 20261122T044950Z

Two dev servers (`live1`/`live2`) on the build that contains `BossEventSyncManager` and
`ServerBossEventMixin`; one headless bot on each server. The bots log the clientbound
`boss_bar` packet (UUID, action, title, health, colour, flags).

## ADD

`/bossbar add mfboss {"text":"MultiForge Boss"}` on `live1`, then `players @a`. Both clients
received the same add packet:

```
[bot] BOSSBAR {"uuid":"fd953d27-45e6-4520-bfe6-409077b1bcfc","action":0,
               "title":"{\"text\":\"MultiForge Boss\"}","health":0.5,"color":1,"flags":0}
```

The UUID, title, health and colour are identical on both sides; the second server did not
create a local `ServerBossEvent`, it replayed the vanilla packet to its player.

## PROGRESS

`/bossbar set mfboss value 25` produced an update on both:

```
[bot] BOSSBAR {"uuid":"fd953d27-...","action":2,"health":0.25}
```

## REMOVE

`/bossbar set mfboss players` followed by `/bossbar remove mfboss` produced:

```
[bot] BOSSBAR {"uuid":"fd953d27-...","action":1}
```

## What this covers and what it does not

This is the same `ServerBossEvent` path used by the dragon fight and raids, so their bars now
appear on every server without duplicating the fight logic. The **raid/dragon fight state**
(waves, phase transitions, raid NBT) is still simulated only by the owner and is not
transferred by this packet; that remains a separate TODO item. The mixin was also observed
loading in the dedicated mod-pack run (`Mixing ServerBossEventMixin ... into
net.minecraft.server.level.ServerBossEvent`).

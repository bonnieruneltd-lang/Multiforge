# BungeeCord plugin evidence 2026-11-22

The BungeeCord counterpart of the Velocity plugin was built and exercised on this tree. The
standalone master remains the default; the plugin is optional.

## Build

```
./gradlew :multiforge-bungee:build
multiforge-bungee/build/libs/multiforge-bungee-1.0.0-alpha.1.jar  (7.1 MB, self-contained)
```

## Proxy choice

The current BungeeCord Jenkins build is for Minecraft 26.1 and closed a 1.20.1 client
immediately. **Waterfall 1.20 build 578** (`waterfall-1.20-578.jar`, the BungeeCord fork with
the 1.20 protocol) was used for the 1.20.1 Forge backends; the plugin loads unchanged because
Waterfall keeps the BungeeCord plugin API.

The full RCON harness passed **18/18** against this BungeeCord-hosted cluster: master
connected, membership, blocks both directions, chest inventory, scoreboard, entity
mirror/damage/removal, sign, time, gamerule, single owner, 20 TPS and save-all

The harness needed one fix to run behind a proxy: it now asks for the **player's own chunk** on
either backend and waits for ownership, instead of relying on the truncated chat listing. That
is a test-harness change only (`tools/compat/cluster_check.py`).

## Limits

* Waterfall 1.20 is required for a 1.20.1 backend; the current BungeeCord build targets a newer
  protocol. The plugin itself uses only the stable BungeeCord API.
* Embedded mode does not start the built-in Minecraft proxy, Prometheus endpoint or leader
  election; use the standalone master for those.
* Waterfall `servers` names must equal the Forge servers' `server.name` values. This run used
  `online_mode=false` and `ip_forward=false`, as the test cluster does.
* The plugin is a self-contained jar (master + protocol + Netty + NBT/YAML/logging); rebuild it
  when those modules change.
